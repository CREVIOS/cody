\section{Identify and Justify Design Patterns}

\subsection{Builder Pattern}

\subsubsection{Purpose and UML Diagram}

The \textbf{Builder Pattern} is a creational design pattern that separates the construction of a complex object from its representation, allowing the same construction process to create different representations.

\noindent\textbf{UML Diagram:}





\subsubsection{Problem Solved}

\textbf{Location:} \texttt{SBackend/services/containerBuilder.js}

The Builder pattern solves the problem of constructing complex Docker container configurations with numerous optional parameters. Without this pattern, we would face:

\begin{enumerate}[label=\arabic*.]
    \item \textbf{Telescoping Constructor Anti-pattern:} A constructor with 20+ parameters would be unmaintainable.
    \item \textbf{Inflexibility:} Different container types would require separate constructors.
    \item \textbf{Readability Issues:} Passing multiple configuration objects would be confusing.
\end{enumerate}

Without the Builder pattern, container configuration would require massive inline configuration objects with 50+ nested parameters, making the code unmaintainable and difficult to test.

\paragraph{Benefits:}
\begin{itemize}
    \item \textbf{Method Chaining:} Fluent interface improves readability.
    \item \textbf{Step-by-step Construction:} Complex objects are built incrementally.
    \item \textbf{Reusability:} Common patterns encapsulated in methods like \texttt{createSandboxConfiguration()}.
    \item \textbf{Validation:} Validation logic can be added before invoking \texttt{build()}.
    \item \textbf{Modularity:} Each builder method handles a specific configuration aspect, improving maintainability.
    \item \textbf{Extensibility:} New builders (e.g., \texttt{DevelopmentContainerBuilder},  \texttt{ProductionContainerBuilder}) can be added without modifying existing code, adhering to the Open/Closed Principle.
\end{itemize}

\subsection{State Pattern}

\subsubsection{Purpose and UML Diagram}

The State pattern is a behavioral design pattern that allows an object to alter its behavior when its internal state changes, making the object appear to change its class.

\subsubsection{Problem Solved}

\noindent\textbf{Location:} \texttt{SBackend/services/containerStates.js}

The State pattern solves the problem of managing container lifecycle states (stopped, running, paused, error, removed) without using complex conditional logic.

Without the State pattern, container lifecycle management would require complex if-else chains in every method, checking the current state and handling transitions manually. This leads to error-prone code where invalid operations can be attempted and state transitions are scattered throughout the service.

\noindent\textbf{Benefits:}
\begin{itemize}
    \item \textbf{Eliminates Conditionals:} No more if-else chains for state transitions.
    \item \textbf{Single Responsibility:} Each state class handles one state's behavior.
    \item \textbf{Open/Closed Principle:} Add new states without modifying existing code.
    \item \textbf{Type Safety:} Each state can have different method signatures.
    \item \textbf{Event Emission:} State transitions emit events for monitoring.
\end{itemize}

\subsection{Strategy Pattern (Backend - Permission System)}

\subsubsection{Purpose and UML Diagram}

The \textbf{Strategy Pattern} is a behavioral design pattern that defines a family of algorithms, encapsulates each one, and makes them interchangeable at runtime. It allows the algorithm to vary independently from clients that use it.

\noindent\textbf{UML Diagram:}

% (Insert UML Diagram Here — e.g., via Mermaid or image)

\subsubsection{Problem Solved}

\begin{itemize}
    \item Previous implementation incorrectly used the \textbf{Chain of Responsibility} pattern.
    \item Sequential chain traversal (\(O(n)\) complexity) for simple role-based permission checks.
    \item Wrong abstraction for a flat role system.
\end{itemize}

\subsubsection{Location}

\begin{itemize}
    \item \texttt{Backend/services/permission\_strategies.py} (328 lines)
    \item \texttt{Backend/services/permission\_enforcer.py} (uses Strategy pattern)
\end{itemize}

\subsubsection{Justification}

\begin{itemize}
    \item The \textbf{Strategy Pattern} is the correct choice for this problem (one task, multiple algorithms, interchangeable).
    \item The \textbf{Chain of Responsibility} was incorrect (no sequential handling needed).
    \item \textbf{Performance improvement:} \(O(n) \rightarrow O(1)\) permission checks.
    \item \textbf{Encapsulation:} Each role's logic is self-contained and easily extendable.
\end{itemize}

\subsection{Factory Pattern (Backend - Router Initialization)}

\subsubsection{Purpose and UML Diagram}

The \textbf{Factory Pattern} is a creational design pattern that provides an interface for creating objects without specifying their exact classes. It centralizes object creation logic and allows the system to decide which class to instantiate.

\noindent\textbf{UML Diagram:}

% (Insert UML Diagram Here — e.g., via Mermaid or image)

\subsubsection{Problem Solved}

\noindent\textbf{Location:} \texttt{Backend/factories/router\_factory.py} and \texttt{Backend/main.py}

The Factory pattern solves the problem of manually importing and registering multiple API routers in the FastAPI application. Without this pattern, we would face:

\begin{enumerate}[label=\arabic*.]
    \item \textbf{Repetitive Boilerplate:} 13 import lines and 13 registration lines in main.py (26 lines total).
    \item \textbf{Maintenance Burden:} Adding a new router requires modifying main.py in two places.
    \item \textbf{Error-Prone:} Easy to make mistakes with typos, wrong prefixes, or inconsistent configuration.
    \item \textbf{No Consistency:} Each router registration could have different configurations.
\end{enumerate}

Without the Factory pattern, router registration would require manual imports and registrations for each router, making the codebase fragile and difficult to maintain as the number of routers grows.

\subsubsection{Location}

\begin{itemize}
    \item \texttt{Backend/factories/router\_factory.py} (266 lines)
    \item \texttt{Backend/main.py} (uses Factory pattern)
\end{itemize}

\subsubsection{Justification}

\begin{itemize}
    \item The \textbf{Factory Pattern} is ideal for centralizing router creation and registration logic.
    \item \textbf{Auto-Discovery:} Automatically finds and registers all routers in the routers directory.
    \item \textbf{Code Reduction:} 26 lines reduced to 3 lines (88\% reduction).
    \item \textbf{Open/Closed Principle:} New routers can be added without modifying existing code.
    \item \textbf{Consistency:} All routers get the same default configuration automatically.
\end{itemize}

\subsection{Observer Pattern (Frontend - Event System)}

\subsubsection{Purpose and UML Diagram}

The \textbf{Observer Pattern} (also known as Publish-Subscribe) is a behavioral design pattern that defines a one-to-many dependency between objects. When one object changes state, all dependent objects are notified and updated automatically.

\noindent\textbf{UML Diagram:}

% (Insert UML Diagram Here — e.g., via Mermaid or image)

\subsubsection{Problem Solved}

\noindent\textbf{Location:} \texttt{Frontend/app/lib/events/EventBus.ts} and \texttt{Frontend/app/lib/events/useEventBus.ts}

The Observer pattern solves the problem of tight coupling between components through prop drilling and direct callbacks. Without this pattern, we would face:

\begin{enumerate}[label=\arabic*.]
    \item \textbf{Tight Coupling:} Components need direct references to notify other components.
    \item \textbf{Prop Drilling:} Parent components must pass callbacks through multiple levels.
    \item \textbf{Inflexibility:} Adding new listeners requires modifying existing components.
    \item \textbf{Testing Difficulty:} Components cannot be tested in isolation due to dependencies.
\end{enumerate}

Without the Observer pattern, components would be tightly coupled through props and callbacks, making the system rigid and difficult to extend. File changes, user presence, and notifications would require manual coordination between components.

\subsubsection{Location}

\begin{itemize}
    \item \texttt{Frontend/app/lib/events/EventBus.ts} (400+ lines)
    \item \texttt{Frontend/app/lib/events/useEventBus.ts} (158 lines)
    \item \texttt{Frontend/app/components/examples/EventBusExample.tsx} (example implementation)
\end{itemize}

\subsubsection{Justification}

\begin{itemize}
    \item The \textbf{Observer Pattern} enables loose coupling between publishers and subscribers.
    \item \textbf{Decoupling:} Publishers don't need to know about subscribers.
    \item \textbf{Scalability:} Easy to add new event types and subscribers without modifying existing code.
    \item \textbf{1-to-Many Communication:} One event can notify multiple independent subscribers.
    \item \textbf{React Integration:} Custom hooks provide automatic cleanup on component unmount.
\end{itemize}

async createContainer(projectId) {
  const builder = new SandboxContainerBuilder();
  const director = new ContainerDirector(builder);
  const containerConfig = director.buildSandboxContainer(
    projectId,
    containerName,
    workspacePath,
    this.IMAGE_NAME,
    {

\subsection{State Pattern Refactoring}

\subsubsection*{Before Architecture (Without State Pattern)}

\noindent\textbf{Location:} \texttt{SBackend/services/containerService.js} (before refactoring)

\noindent\textbf{Problems:}
\begin{itemize}
    \item Complex conditional logic with if/else chains for state transitions
    \item No state tracking — current container state unknown
    \item Error-prone — invalid operations may be called (e.g., start already running container)
    \item No validation — cannot check if operation is allowed before attempting
    \item Tight coupling — service directly manages all state transitions
\end{itemize}

\begin{lstlisting}[style=vscodejs, caption={Container Service before refactoring (without State Pattern)}]
// SBackend/services/containerService.js (OLD CODE)
async createContainer(projectId) {
  // ... container creation ...
  const container = await this.docker.createContainer(containerConfig);
  try {
    await container.start();
    console.log('Container started');
  } catch (error) {
    console.error('Failed to start:', error);
  }
}

async stopContainer(projectId) {
  const containerInfo = this.containers.get(projectId);
  if (!containerInfo) return;

  const container = this.docker.getContainer(containerInfo.id);
  try {
    const info = await container.inspect();
    if (info.State.Status === 'running') {
      await container.stop({ t: 10 });
      console.log('Container stopped');
    } else if (info.State.Status === 'exited') {
      console.log('Container already stopped');
    } else if (info.State.Status === 'paused') {
      await container.unpause();
      await container.stop({ t: 10 });
      console.log('Container unpaused and stopped');
    } else {
      console.log('Container in unknown state:', info.State.Status);
    }
  } catch (error) {
    console.error('Error stopping container:', error);
  }
}

async restartContainer(projectId) {
  // More if/else chains for restart logic
}

  await containerWrapper.start(); // Delegates to StoppedState.start()
}

async stopContainer(projectId) {
  const containerWrapper = this.containers.get(projectId);
  if (!containerWrapper) return;
  await containerWrapper.stop(); // Delegates to current state
}

async restartContainer(projectId) {
  const containerWrapper = this.containers.get(projectId);
  if (!containerWrapper) return;
  await containerWrapper.restart(); // Delegates to current state
}
\end{lstlisting}

    \item Separates concerns across state classes
    \item Emits events during state transitions for monitoring
    \item Provides automatic recovery via \texttt{ErrorState}

            "canManageMembers"
        }

            "canEdit", "canLock", "canView", "canInvite",
            "canApproveLock", "canRequestLock"
        }
        granted = permission in maintainer_permissions

        viewer_permissions = {"canView"}

\noindent\textbf{Example After (With Observer Pattern):}

// Publisher - Completely decoupled!
function FileEditor() {
  const publish = useEventPublisher();

  const handleSave = () => {
    // Just publish - don't care who's listening!
    publish({
      type: EventType.FILE_UPDATED,
      fileId: file.id,
      fileName: file.name,
      projectId: currentProject,
      timestamp: Date.now()
    });
  };
  return <button onClick={handleSave}>Save</button>;
}

// Subscriber - Completely independent
function ActivityLog() {
  useEventBus(EventType.FILE_UPDATED, (event) => {
    addToLog(`File ${event.fileName} updated`);
  });
  return <div>{/* activity log UI */}</div>;
}
\end{lstlisting}

\noindent\textbf{Implementation Details:}

\noindent The EventBus implements the Observer pattern as a singleton with subscription management. React hooks (\texttt{useEventBus}, \texttt{useEventPublisher}) provide automatic cleanup on component unmount, preventing memory leaks.

\noindent\textbf{Benefits Achieved:}
\begin{itemize}
    \item Complete decoupling: Publishers don't know about subscribers
    \item Eliminated prop drilling: No need to pass callbacks through component hierarchy
    \item Scalability: Easy to add new subscribers without modifying publishers
    \item Testability: Components can be tested in complete isolation
    \item 1-to-Many Communication: One event can notify multiple independent subscribers
    \item Automatic Cleanup: React hooks handle subscription cleanup on unmount
\end{itemize}

\section{Reflection and Testing}

\subsection{Reflection: Improvements and Trade-offs}

\subsubsection*{Improvements Achieved}
\begin{enumerate}
    \item \textbf{Modularity} – All five patterns encapsulate complex logic into well-defined, reusable components. Each pattern addresses a specific concern: Builder for object construction, State for lifecycle management, Strategy for algorithm selection, Factory for object creation, and Observer for event communication.
    \item \textbf{Maintainability} – Patterns separate concerns and improve organization. The Strategy pattern replaced incorrect Chain of Responsibility with O(1) permission checks. Factory pattern reduced router registration from 26 lines to 3 lines (88\% reduction). Builder pattern eliminated 100+ line configuration objects.
    \item \textbf{Testability} – Patterns enable isolated unit testing. Each pattern has comprehensive test suites: Strategy (15+ tests, 94\% coverage), Factory (20 tests, 92\% coverage), Observer (25+ tests, 96\% coverage), Builder (15+ tests), and State (20+ tests).
    \item \textbf{Scalability} – Open/Closed principle supported across all patterns. New routers auto-register via Factory. New roles can be added via Strategy without modifying existing code. New event subscribers can be added via Observer without touching publishers.
    \item \textbf{Readability} – Builder and State patterns simplify complex Docker container management. Method chaining in Builder provides fluent interface. State pattern eliminates complex if/else chains for container lifecycle.
    \item \textbf{Performance} – Strategy pattern improved permission checks from O(n) chain traversal to O(1) direct lookup (77\% faster). Factory pattern scales linearly with router count (tested with 1-20 routers).
    \item \textbf{Decoupling} – Observer pattern achieved complete component decoupling, eliminating prop drilling and tight coupling in the frontend.
\end{enumerate}

\subsubsection*{Trade-offs}
\begin{itemize}
    \item \textbf{Abstraction Complexity} – Additional abstraction increases learning curve for new developers. Patterns require understanding of design principles (SOLID, encapsulation, polymorphism).
    \item \textbf{Performance Overhead} – Slight performance overhead from abstraction layers (negligible in practice: sub-millisecond for permission checks, router registration happens at startup).
    \item \textbf{Code Volume} – More classes and interfaces required initially (Strategy: 5 strategy classes + factory, Factory: RouterFactory + RouterConfig, Observer: EventBus + hooks, Builder: Abstract builder + concrete builders + director, State: 6 state classes + wrapper).
    \item \textbf{Debugging Complexity} – Observer pattern makes event flow harder to trace in IDE (mitigated by event history feature). Factory pattern uses dynamic imports (reflection) which can be harder to debug.
    \item \textbf{Memory Management} – Observer pattern requires careful subscription cleanup to prevent memory leaks (mitigated by React hooks with automatic cleanup).
\end{itemize}

\subsubsection*{Design Decisions}
\begin{enumerate}
    \item \textbf{Builder Pattern} – Applied to Docker container configuration to handle 50+ configuration parameters. Uses Director pattern to orchestrate complex construction sequences. Provides validation before object creation.
    \item \textbf{State Pattern} – Applied to container lifecycle management (stopped, running, paused, error, removed, creating). Eliminates conditional logic and enforces valid state transitions. Emits events for monitoring.
    \item \textbf{Strategy Pattern} – Replaced incorrect Chain of Responsibility pattern for permission system. Provides O(1) permission checks vs O(n) chain traversal. Supports runtime strategy switching and data-driven custom roles.
    \item \textbf{Factory Pattern} – Centralizes router discovery and registration. Auto-discovers routers in directory, eliminating manual imports. Enforces consistent configuration across all routers.
    \item \textbf{Observer Pattern} – Implements Pub/Sub for frontend component communication. Singleton EventBus with 16+ event types. React hooks provide automatic cleanup. Supports wildcard subscriptions and event history.
\end{enumerate}
